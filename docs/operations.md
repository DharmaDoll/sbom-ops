# 運用ガイド

初めての方は[最短の初回確認](getting-started.md#最短の初回確認外部通信なし)から始める。
担当と作業のタイミングは[利用シーン](use-cases.md)で確認できる。
コマンドはリポジトリのルートで実行し、通常運用は`--no-github`を指定する。

資産登録・成果物根拠・期限付き稼働申告・速報の取得と照合は利用できる。
CIへの生成ジョブの組込みと定期実行の設定は導入者が行う。
配備先の自動発見・Runtime SBOMの自動生成は未提供。
Slack通知は[予定本文を標準出力で確認](slack-notifications.md)でき、通常syncからは送信しない。
セキュリティ担当が対応判断を記録し、開発担当へ引き渡す。GitHubの自動起票は前提にしない。

## 利用者の作業一覧：いつ・どこで・何をするか

初回は導入準備 → Build SBOM投入 → 配備先との対応確認 → 日常の確認の順に進める。
Source SBOMは早期確認を補助する。運用時は既存のBuild SBOMと配置情報を結び付ける。
以下の「確認結果」は、その工程で利用者が残す根拠であり、ツールの成功表示だけで代用しない。

| タイミング | 担当・操作場所 | 利用者の作業と手順 | 残すもの・確認結果 |
| --- | --- | --- | --- |
| 導入・新サービス追加 | サービス／運用担当、sbom-ops CLI | [登録単位と開始順序](assets.md#登録単位と新規サービスの開始順序)に沿ってサービス・配布単位・担当を登録。CI担当はDT接続先と投入権限を準備 | サービスID・配布単位ID・担当と、送信先の合意 |
| PR・依存更新 | 開発担当、開発CI | 依存定義等からSource SBOMを生成し早期確認。[根拠登録](assets.md#sourcebuild根拠の登録と訂正)でソース版と文書参照を保持 | commit、元文書、生成ツール・版。Build SBOMとは区別し、同じDT Projectへ上書きしない |
| リリース候補・配布物の生成 | CI担当、ビルドCI → DT | [最終イメージの生成・投入手順](sbom-input.md#コンテナのsbomを生成してdtへ送るタイミング)をCIに組み込む。OSパッケージとアプリ依存の収録を確認 | イメージdigest、元SBOMとハッシュ、CI実行参照、DT Project、処理結果。受付と解析結果を区別 |
| 初回配備・新版への切替・再配備 | 運用担当、実際の配備先とsbom-ops CLI | 配備した成果物を確認し、[Projectの照合](assets.md#dtから読み戻して紐づける方法)と[稼働情報の登録](assets.md#配備変更と稼働申告)を行う | 環境、成果物ID、確認者・日時・根拠・有効期限。新旧並存なら両方保持 |
| 日常・脆弱性の速報 | セキュリティ／運用担当、DTとsbom-ops CLI | [日常の流れ](daily-operations.md#日常の流れ)でsync結果を確認。[逆引き](investigation.md#保存済みの結果からcve部品を逆引きする)で影響候補を探し、担当と次の行動を確認 | 対象資産、担当、確認日時、不足情報、対応判断。古い保存結果や一致なしを安全の証明にしない |
| 修正・旧版停止・担当変更 | 開発／運用担当、CI・配備先・sbom-ops CLI | 再ビルドして新SBOMを投入し、[更新・担当変更・停止](daily-operations.md#同じサービスで更新担当変更停止を通す)を記録。セキュリティ担当が修正を確認 | 新版の根拠、旧版停止の根拠、変更履歴。Finding消失だけで修正完了にしない |
| SBOMの収録漏れ・誤記を発見 | CI／運用担当、CI成果物保管先・DT・sbom-ops CLI | 同じ成果物のSBOMを訂正して再投入し、[根拠の訂正](assets.md#sourcebuild根拠の登録と訂正)を記録 | 成果物IDは維持、文書の版・ハッシュ・訂正理由と旧記録を保持 |

DTは構成・Finding・分析状態を保持する。元SBOMとCI証拠はCI成果物保管先、
サービス・担当・配置申告と対応関係はsbom-opsの資産台帳へ保存する。
対応判断と修正作業は担当者が管理する。製品のGitHub Issues自動同期は本番有効化を保留しており、
この一覧の作業で自動的に有効にはならない。

調達担当は外部製品の供給元に対象製品・版のSBOMと署名情報を要求し、組織の受入手順で
対象との一致や出所を確認する。基盤担当は共通ベースイメージのSBOMと対象digestを提供し、
サービス担当は採用したベースを記録したうえで、自分たちの最終イメージからもBuild SBOMを生成する。
供給元署名の検証・隔離受入、署名済みベースイメージの配布基盤は本PJでは未提供であり、
DTへの取込成功をその検証の代わりにしない。

この整理は[利用者提示のライフサイクル指針](https://github.com/DharmaDoll/product-security-guidance/blob/main/sources/user-supplied/user-supplied-sbom-lifecycle-guidance-ja.md)
を本PJの操作へ対応付けたもの。Source／Build／運用の観測を分ける方針は
[仕様の結合契約](../SPEC.md#sbomライフサイクルの結合契約後続実装の基準)に従う。
現在の運用情報は人の申告・照合が中心で、Runtime SBOMの自動生成、実行メモリの完全な収集、
デプロイ基盤の自動発見は提供していない。Build SBOMも生成器の網羅性を保証しない。

## YAML configuration

設定例は[examples/config.yaml](../examples/config.yaml)、契約は
[SPEC](../SPEC.md#configuration-contract)に集約する。
CLI → 環境変数 → YAML → 既定値の順で、YAMLの秘密情報は `env:変数名` で参照する。
KEVキャッシュは任意。`--refresh-kev` はTTL内でも再検証し、
取得失敗時に古い値を使うには明示設定が必要。結果の `kev_used_stale_cache` を確認する。
